# ТЗ №8 — Qwen3-VL: описание окружающей сцены

Дата испытаний: 21 ноября 2026, Asia/Qyzylorda. Репозиторий: существующий AI Navigation Assistant.

**Интеграция реализована и проверена на Windows и CPH2727 / Android 16 / ARM64.**
Ручная кнопка использует локальную Qwen3-VL через FastAPI. Offline YOLO и
Safety остаются независимыми от VLM. Качество модели имеет ограничения,
перечисленные ниже; описание не является оценкой безопасности движения.

## Реализация

Один существующий camera stream обслуживает локальную детекцию и однократный
VLM-запрос. При нажатии «Описать окружение» следующий доступный кадр
передаётся существующему encoder isolate. Повторные нажатия не создают запросов.
Сохранён только один CameraController; `takePicture`, второй поток и
постоянный VLM-анализ не используются.

Изображение: NV21 → RGB → JPEG quality 78, большая сторона до 640 пикселей,
с сохранением пропорций. На телефоне фактические JPEG — 360×640.
Конвертация/поворот выполняются вне UI isolate; буфер копируется только
для выбранного кадра. Для задней камеры отражение не применяется.
Ориентация и стороны проверены тестом с четырьмя различными углами изображения,
а также положительными оценками пользователя на реальных сценах.

Новый `VlmService` проверяет свежесть **до отправки**: не старше 1500 мс,
допустимый размер JPEG, текущую сессию. После ответа сверяются `request_id`,
`captured_at`, статус и текст. Длительная обработка не превращает снимок
в просроченное Safety-предупреждение: описание начинается с «На снимке»
или «На момент съёмки». Время ответа измеряется до постановки текста в TTS,
а не до конца прочтения всего текста.

HTTP-запрос отменяется через `AbortableMultipartRequest`; backend дополнительно
получает DELETE отмены. При отмене/закрытии камеры/сворачивании приложение
синхронно инвалидирует поколение запроса. Поздний ответ не озвучивается.

В существующий SafetyTtsService добавлена принадлежность ручного сообщения
конкретному запросу и проверка его актуальности непосредственно перед речью.
Отмена VLM удаляет только его сообщение; активное автоматическое предупреждение
не останавливается. Второй FlutterTTS не создаётся. Приоритеты 3/2/1,
cooldown 12/20/30 с, Safety TTL и алгоритм подтверждения объектов не менялись.
TTL очереди ручных сообщений считается от получения ответа, а не от съёмки.

«Что впереди?» продолжает использовать SmartSceneAnalyzer. Vosk остаётся
диагностическим: голосовая команда к VLM в этой задаче не подключалась,
`VOSK_ACTIONS_ENABLED` по умолчанию false.

## FastAPI и Ollama

Расширен существующий `backend/server.py`, новый FastAPI-проект не создавался.
VLM не вызывает `analyze`, YOLO или Depth. Повторная загрузка YOLO на запрос
не выполняется. Для необязательного Depth его импорт перенесён внутрь
существующего условия `DEPTH_ENABLED`; файлы и алгоритмы Depth не изменены.
На испытательном запуске использовалось `DEPTH_ENABLED=false`.

Контракт `POST /vlm/describe`: multipart с одним `image` типа `image/jpeg`,
`question`, уникальным `request_id`, `captured_at` с часовым поясом.
Возвращаются описание, модель, исходная дата съёмки, время обработки,
размеры изображения и диагностические времена Ollama.

Ограничения и обработка:

- JPEG до 768 KiB, изображение до 4 194 304 пикселей, обязательное декодирование
  и проверка Pillow. Backend уменьшает большие изображения до 768 пикселей.
- ASGI-лимит multipart-тела — JPEG-лимит +32 KiB, включая chunked-запросы.
  Это ниже 1 MiB spool-порога проверенной Starlette 0.50.0: принятый файл
  остаётся в памяти. После обработки UploadFile закрывается; JPEG и base64
  не пишутся на диск и не попадают в журнал запросов.
- `/api/chat`, настоящее base64-изображение в user message, `stream=false`.
  System prompt вынесен в `backend/prompts/scene_description.txt`.
- Один активный запрос, без неограниченной очереди. При занятости — HTTP 429
  с Retry-After. Ограничены длина вопроса, ответа и число выходных токенов.
- Неправильный JPEG — 400, превышение размера — 413, недоступность/ошибка
  модели — 503, timeout — 504. Отменённый запрос может завершиться 499.
- Backend timeout 45 с, Flutter timeout 50 с. Disconnect проверяется backend;
  `DELETE /vlm/requests/{id}` отменяет задачу владельца запроса.
- Пустой, слишком длинный или незавершённый ответ отклоняется. Дополнительный
  фильтр отклоняет известные формулировки указаний движения, утверждения
  «путь свободен/безопасен» и числовые расстояния в метрах. Это не проверка
  фактической правильности всех остальных деталей модели.

Ollama 0.40.13 проверена через `/api/version`; требование ≥0.12.7 выполнено.
Точная модель: **qwen3-vl:2b-instruct**, digest `afc393e3572c…`, Q4_K_M,
локальный runner `llamacpp`, capability `vision` подтверждена `/api/show`.
Другая модель не подставлялась; существующая Gemma не использовалась.
Ollama слушает `127.0.0.1:11434`, клиент backend запрещает удалённый/cloud URL
и использует `trust_env=false`. `keep_alive=10m` сохраняет прогретую модель.

Параметры: `num_ctx=2048`, `num_predict=160`, `temperature=0.15`, `seed=7`.
На RTX 3050 Laptop / 4096 MiB `ollama ps` показал **100% GPU**.
Дополнительный CPU offloading не потребовался; размер модели на диске
не использовался как оценка VRAM.

Первичные источники: [карточка Qwen3-VL](https://ollama.com/library/qwen3-vl:2b-instruct),
[Ollama chat API](https://docs.ollama.com/api/chat),
[список запущенных моделей и size_vram](https://docs.ollama.com/api/ps).
Фактические сведения установки: `qwen3_vl_model_info.json`.

## Измерения

Ноутбук: Windows, RTX 3050 Laptop 4 GB, системная RAM около 15,75 GiB.
Холодный запрос выполнен с настоящим `backend/test.jpg`, затем проведены
20 отдельных запросов по размеченным изображениям. На Android сохранены
**20 полных успешных HTTP-ответов** по свежим кадрам физической камеры,
помимо отменённых и отрицательных сценариев.

| Метрика | Результат |
|---|---:|
| Холодный JPEG → FastAPI → ответ | 28 443,7 мс |
| Загрузка модели в холодном запросе | 13 274,7 мс |
| Cold prompt/image evaluation | 13 392,6 мс |
| Cold generation | 1048,8 мс |
| Backend: тёплый HTTP p50 / p95, 20 запросов | 2075,2 / 3451,8 мс |
| Backend JPEG preprocessing p50 / p95 | 5,18 / 10,78 мс |
| Ollama prompt/image evaluation p50 / p95 | 877,7 / 902,99 мс |
| Ollama generation p50 / p95 | 747,56 / 1053,86 мс |
| Android: JPEG preparation p50 / p95 | 301,77 / 371,63 мс |
| Android: HTTP roundtrip p50 / p95, включая backend/VLM | 2510,03 / 2690,30 мс |
| Android: полный ответ p50 / p95, до TTS | **3026,09 / 3334,86 мс** |
| Пиковая занятость GPU по nvidia-smi | 2677 MiB |

Цель тёплого ответа до 5 с выполнена в измеренных сериях. Холодный запуск
существенно медленнее и не скрывается усреднением с тёплыми запросами.
В последних пяти Android-замерах речь намеренно отменялась **после получения
JSON**, чтобы измерять ответ отдельно от продолжительности прочтения.

Источники: `qwen3_vl_first_real_image.json`, `qwen3_vl_backend_benchmark.json`,
`qwen3_vl_resource_probe.json`, `qwen3_vl_android_validation.json`.
RSS — сумма Windows working sets, не уникальная или гарантированно необходимая
RAM. В первоначальном мониторе имя `llama-server.exe` не входило в RSS-сумму;
его значения помечены как неполные. Для приведённого RAM использован отдельный
исправленный замер всех трёх процессов; исходные ответы и измерения не удалены.

### YOLO при работе VLM

После прогрева выполнен протокол A–B–B–A, четыре окна по 20 с. В каждом B
запускался ограниченный запрос по свежему кадру; фактически один за окно,
включая последующее озвучивание. Safety оставался активен.

| Окно | VLM | YOLO результатов/с | Camera-to-result p50 / p95, мс |
|---:|---|---:|---:|
| 1 | нет | 3,30 | 249,1 / 514,9 |
| 2 | по запросу | 3,45 | 236,2 / 411,8 |
| 3 | по запросу | 3,40 | 234,5 / 459,6 |
| 4 | нет | 4,20 | 201,5 / 265,7 |

Среднее: **3,75/с без VLM против 3,425/с с VLM, −8,7%**.
Блокировки YOLO ожиданием сервера не обнаружено; детекции продолжаются
во всех активных окнах. Базовые окна различаются заметно, поэтому четыре
коротких окна не доказывают статистическое отсутствие регрессии. Числовой
порог «существенной регрессии» ТЗ не задаёт; измеренную разницу нужно
учитывать при приёмке, не объявляя её нулевой.

## Качество: 20 размеченных изображений

Использован уже имевшийся локальный ROD test split:
`abtinzandi/obstacle-detection-dataset`, версия 4. Набор: 16 оригиналов
и 4 контролируемых варианта с затемнением/размытием. Есть лестницы,
лестничная площадка с дверями/проходом, мебель в комнате, люди, автомобили,
уличные объекты и несколько объектов одновременно.

`qwen3_vl_quality_manifest.json` содержит источник, SHA256 и разметку объектов
с нормированными bbox/сторонами. `qwen3_vl_quality_review.json` содержит для
всех 20 ответов найденные/ошибочные объекты, пропуски, оценку направлений,
галлюцинации, длину и понятность. Разметка ROD неполная: отсутствие класса
в dataset labels не считалось доказательством галлюцинации. Спорные сцены
дополнительно проверены по полному изображению.

Выявлено:

- №2: выдуманные руки на перилах. На изображении людей нет.
- №5: один стул назван во множественном числе, грамматическая ошибка.
- №7–8: неподтверждённая интерпретация текстового оверлея как цен/условий.
- №12: выдуманные стены по сторонам перехода.
- №13: ошибочный материал ограждения и китайское слово внутри русского текста.
- №15: пропущена хорошо заметная входная дверь справа.
- На части тёмных/размытых кадров ограничения объяснены недостаточно явно.

Основные объекты обычно распознаны, но prompt не устранил выдуманные детали.
Неподтверждённых указаний движения или заверений в безопасности пути
в этих 20 ответах не обнаружено. Это ограниченная визуальная проверка,
не гарантия фактической точности и не оценка пригодности для самостоятельной
навигации. Снимки создаются только как тестовые fixtures; обычные backend
и приложение изображения не сохраняют.

На телефоне получены **8 положительных оценок пользователя** для знакомых
комнатных сцен и двери: объекты и стороны соответствовали сцене.
Коридор/лестница в реальном обходе пользователем не подтверждались;
они проверены на изображениях, а приоритет TTS — отдельным тестовым сигналом.

## Android: функциональные проверки и отказы

Фактические цепочки: задняя камера → JPEG 360×640 → Wi-Fi LAN → существующий
FastAPI → локальная Ollama → русский текст → общий SafetyTtsService.
Тестовый сигнал `Тест: приоритет три` — инъекция подтверждённого alert,
а не заявление о физическом препятствии.

Подтверждены запуск камеры и ручного YOLO; свежий JPEG; русский ответ и
озвучивание; работа YOLO во время запроса; приоритетное прерывание VLM;
повторное нажатие; отмена; закрытие камеры; запрет использования старого кадра;
сворачивание; отключение Wi-Fi; недоступность FastAPI; недоступность Ollama;
backend timeout; повторное подключение.

При отказах выводится/озвучивается «Подробное описание сейчас недоступно».
YOLO остаётся запущен. Локальный SmartSceneAnalyzer не подставляется вместо
VLM-ответа. Wi-Fi и обычная конфигурация backend после тестов восстановлены.

Методы проверки отказов раскрыты в `qwen3_vl_android_failure_tests.json`:
FastAPI действительно останавливался; для недоступности Ollama тот же app
временно направлялся на недоступный loopback-порт 11435; для timeout
временно устанавливался лимит 1 с, на сервере получен реальный HTTP 504.
После проверки возвращены 11434 и 45 с. Отдельные backend-тесты проверяют
HTTP 404 отсутствующей модели → HTTP 503.

Сохранены и ошибки стенда, без скрытого удаления:

- В повторном автотесте в другой сцене искусственная фраза не была отмечена
  в трёхсекундном окне ожидания. Это не считается успешным повтором;
  первый тест прерывания и тесты общего speaker прошли.
- В первой пакетной проверке cancel отправлен после завершения запроса
  (19:34:26 UTC против окончания 19:34:22 UTC), поэтому строка false оставлена.
  Корректный повтор отменил **ещё обрабатываемый** запрос и дал null без речи:
  `qwen3_vl_android_cancel_followup.json`.

## Проверки и эксплуатация

- `flutter analyze`: без замечаний.
- `flutter test`: **136 тестов**, успешно, включая 12 VLM/TTS-тестов,
  3 проверки JPEG/ориентации и существующие Safety/YOLO/Camera/Voice-тесты.
- Backend: **29 тестов**, успешно: 21 VLM и 8 существующих DepthStabilizer.
  Проверены также chunked oversize, занятый слот, отмена и возврат слота.
- Android ARM64 release APK собран. На устройство после диагностики
  установлен обычный `lib/main.dart`, без диагностических флагов.
  SHA256 установленного `base.apk` совпал с финальным APK.
  В этой сборке ручной Start при остановленном FastAPI запустил Offline YOLO
  (на контрольном экране 3,9 результата/с); Stop отработал. Затем проверены
  сообщение при выключенной камере и реальный VLM POST → HTTP 200 с обычной
  кнопки после восстановления FastAPI.
- Обычная сборка по умолчанию выбирает Offline YOLO; запрос VLM не меняет
  режим детекции. Существующий ручной переключатель режима сохранён.

Конфигурация клиента: `VLM_BASE_URL` в `.env` через AppConfig; сейчас
`http://192.168.10.3:8000`. IP не зашит в UI. Сервер привязан к этому
частному Wi-Fi-интерфейсу, VLM-маршруты дополнительно проверяют доверенные CIDR.
Ollama остаётся на loopback. На API images не логируются и не сохраняются.

Повторение в существующем Python-окружении backend:

```powershell
python -m pip install -r backend/requirements-vlm.txt
ollama --version
ollama pull qwen3-vl:2b-instruct
ollama list
$env:OLLAMA_BASE_URL='http://127.0.0.1:11434'
$env:VLM_ALLOWED_NETWORKS='127.0.0.0/8,::1/128,192.168.10.0/24'
$env:DEPTH_ENABLED='false' # конфигурация именно VLM-испытаний
Set-Location backend
python -m uvicorn server:app --host 192.168.10.3 --port 8000
```

CIDR/IP следует заменить на фактическую доверенную локальную сеть.
Работа Depth совместно с VLM на GPU в этой серии не измерялась.
Дополнительные библиотеки: FastAPI 0.122.0, Starlette 0.50.0,
Pillow 12.0.0, httpx 0.28.1. Необязательные зависимости Depth остаются
обязанностью исходного окружения Depth при его включении.

Повторение данных и тестов:

```powershell
python tool/qwen_prepare_quality.py
python tool/qwen_backend_benchmark.py --url http://192.168.10.3:8000
python -m pytest backend/test_vlm.py backend/test_depth_stabilizer.py -q
flutter analyze
flutter test
flutter build apk --release --target-platform android-arm64
```

Функциональный стенд — `tool/qwen_android_validation.dart`; файловое управление
через USB существует только в специальном target и не входит в обычное
приложение. Диагностические getters обычной release-сборки заблокированы.
Финальный APK и состояние восстановления
перечислены в `qwen3_vl_artifacts.json`.
